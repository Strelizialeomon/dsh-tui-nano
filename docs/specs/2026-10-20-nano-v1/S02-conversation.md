# [2026-10-20-nano-v1/S02] 对话与输入

- 组标识：`2026-10-20-nano-v1`；角色：子件 S02，单交付为可真实对话、可编辑输入、可中断并恢复的对话宿主。
- 状态：草案，未批准实施；Issue：待规格合入后创建。
- 总纲：[共享约定与依据](README.md)。上游：S01。下游：D02、D03 的消费者。
- 合入前提：S01 协议与生命周期可用；本份用真实官方会话完成发送、接收、中断和重连验证。发布由 S13 承担。

## 1. 边界

拥有 `crates/nano-app/`、`crates/nano-conversation/`、`bridge/conversation/`。提供有序输入、会话地址、提交与队列、流式接收、消息身份、场景与焦点接口，以及功能注册接口的入口。

不实现 transcript 渲染与差异展示（S03）、模型与命令业务（S04）、技能解析（S05）、附件上传协议（S06）、会话切换与压缩（S07）、子代理导航（S12）。S02 只定义这些功能消费的输入、地址和事件形状，不替它们实现行为。

S02 不保存第二份会话历史。消息、工具结果、队列和中断事实都以官方会话记录为准；Rust 只保留可丢弃的展示缓存、未发送草稿和阅读位置。

## 2. 会话地址与消息身份

每个被驱动的对话用一个地址标识：普通主会话用 `rootSessionId`，子代理用官方直接父地址 `{ parentSessionId, childSessionId, mode }`，`mode` 取 `one-shot`/`continuable`/`unknown`。地址由 S01 握手给出，不能从目录名、标题或窗口标题推断。

展示层可见的每条消息必须有官方来源：

| 展示对象 | 身份来源 | Rust 允许保存 |
| --- | --- | --- |
| 用户消息 | 官方 `user/message` 的 `seq`；提交期用 `requestId`，官方落盘为 `source.rpcId` | 未确认提交的本地回显、草稿 |
| 助手消息 | 官方 `assistant/message` 的 `seq`（attempt 结束才转正） | 流式预览、展开状态 |
| 工具调用与结果 | `tool/call` 的 `callId`；V4 是 tool-role 消息顶层 `data.message.toolCallId`（等于 `source.callId`），V3 才是 `content[0].toolCallId` | 展示展开状态 |
| 队列/待输入 | 官方 `inbox` 投影 | 输入框里的未提交文本 |
| 合成 bash 记录 | Nano 本地 `bash-mode` 标记 + 官方 `inject` 的 UserMessage（`<bash-input>`/`<bash-stdout>`/`<bash-stderr>`）；官方没有 `bash-mode` source | 展示为 bash 记录；不作为用户批准 |
| 失败/中断 | 官方事件（含 `assistant/attempt`）或明确的宿主错误 | 错误展示状态 |

`requestId` 是唯一一次提交的业务身份，在用户按下发送时生成并原样交给官方；它不是 RPC `id`，不能拿 RPC 层的重试编号冒充。官方只在请求已入队或已落 `user/message` 时按 `requestId` 去重；claim 到落盘之间、以及子代理路径没有去重。因此断线后同一 `requestId` 只用于查询官方已接收的事实，不生成第二个 `requestId` 重发。没有官方回执时，状态只能是「未确认」，不能显示成「已发送」或「失败」。

流式助手内容是展示数据，不是历史来源：收到正式 `assistant/message` 后，以该持久消息替换同一 attempt 的预览。失败、重试或取消的 attempt 会落 `assistant/attempt`，此时立即退休预览，不把预览留在历史里。已知 attempt 的 revision、dense-index 或 settlement 缺口才重新打开 follow；未知 attempt 的 live 帧直接忽略，其持久结算照常发布，不能因为中途接入就反复重连。重连后以官方分页和投影重建对话。

## 3. 输入模型

输入是一个有序内容列表：文本段与附件按用户实际顺序排列；附件由 S06 产生，S02 只负责保持顺序和提交边界。纯空白文本且没有附件时不允许提交。

输入行为：

1. 支持多行编辑、括号粘贴（bracketed paste）和中文输入法组合态。组合态未结束时，Enter 属于输入法，不触发发送。
2. 用户原文、代码和粘贴内容按原字节保留；展示层可以归一化控制字符，但复制、编辑和提交必须取原始文本。
3. 草稿按会话地址分别保存，切换会话或进入子对话再返回时恢复；草稿只存在 Rust 内存，不写入官方会话，也不生成历史消息。当前窗口只显示当前地址的草稿，切换后旧草稿不出现。
4. 输入框不承担命令解析。以 `/` 开头的命令由 S04 注册的入口处理，`/技能名` 由 S05 处理，`!` 人工命令由 S08 处理；S02 只提供命令入口和路由，不自行解释业务。`!!` 没有特殊模式，只是原样交给 shell 的普通文本。
5. 发送被拒绝（空内容、附件未就绪、宿主未就绪）时，草稿和附件保留，焦点不丢。归档 Gate 在官方 `agent/pre-step`，writer-held 是 S01 的启动/恢复错误，不是提交时的本地拒绝；S02 不伪造这两类检查。
6. 消息、回显、队列项、附件和预览都按地址归属；切换地址后旧内容不显示、不写入新地址。

草稿的生命周期与窗口所有权一致：关闭窗口后不承诺跨进程恢复；重新打开同一会话时，历史来自官方记录，草稿来自新的空状态。

## 4. 提交、队列与转向

官方只有两种投递语义：`queue`（下一回合）和 `steer`（下一步）。空闲与运行只决定 `queue` 落在 transcript 还是 QueueDock；`followup` 是 `queue` 的 Agent 封装，不是第三种语义。

| 动作 | 官方语义 | 何时可见 | 结果 |
| --- | --- | --- | --- |
| 排队到下一回合 | `queue`/`followup` | 运行中默认；空闲发送也是 `queue` | 留在 inbox，等当前回合结束 |
| 插话到下一步 | `steer` | 会话正在运行、用户明确选择「插话」 | 进入下一步；回合在 claim 前结束则可能落到下一回合 |

默认值：空闲时 Enter 发送（queue）；运行中 Enter 进入下一回合队列，用户可显式选择「插话」改为 `steer`。队列行必须显示「已排队」而不是「已发送」，并允许删除。删除队列项走官方 inbox 变更；删除是持久取消，不保证已经开始的步骤回滚。`steer` 是 best-effort，界面不能承诺它一定在当前回合生效。

发送流程：

1. 冻结本次内容快照，生成 `requestId`，同步插入本地回显；回显只存在于展示内存。
2. 通过 S01 提交；附件先由 S06 完成上传回执，未完成时不允许把半成品提交给官方。
3. 收到官方接受事实后，回显转为「已接收」；正式消息事件到达后，用持久消息替换回显。
4. 明确失败时移除回显并保留草稿；结果未知时保留「未确认」状态，先查询官方 inbox/历史，不自动重发。

同一 `requestId` 只在官方已入队或已落盘时返回原接受；claim 窗口和子代理路径没有官方去重，UI 不得在结果未知时用新 ID 重发。队列内容编辑只接受非空文本；附件不能通过队列编辑后补。编辑带附件的队列项会整体替换成纯文本并丢附件，官方没有「只移除附件」的队列动作，因此必须禁止编辑带附件项。

## 5. 中断与停止

- 用户按停止只结束当前活动回合。公开 Session Controller 的 cancel 只接受 `sessionId` 并硬编码 `keepInbox: true`，所以队列默认保留；没有原子的「停止并清空」官方接口，要清空必须逐项走 inbox 变更再取消。被 claim 的项返回 `session/queue-item-not-found` 时，重新读队列并显示剩余项；不能显示成「已清空」。停止不清空草稿。
- 停止是可取消的请求，不是瞬时事实：已提交、已执行、已持久化是不同状态。停止后必须先收到官方 idle/取消事实，再恢复输入；不能因为界面回到可输入就宣称模型已停。回合终态是 `completed`/`aborted`/`blocked`/`error`/`max-tokens`/`interrupted`/`forked`，自然完成不能被显示成「已终止」；`killed`/`failed` 是任务状态，见 S08。
- 子代理或 Monitor 触发的取消不能借用户停止按钮扩大为清空用户队列；S12/S10 只能取消自己拥有的活动。
- 连接断开时，S02 只重建可观察订阅，不自动另起会写同一会话的宿主。重新连接成功后，只有已入队或已落盘的 `requestId` 能对齐；claim 窗口/子代理路径无法对齐的显示为「未知」，交由用户处理，不自动重发。

## 6. 场景、焦点与功能注册

S02 提供唯一的场景接口（scene）和焦点接口（focus），供 S03-S12 注册视图，避免每个功能各改一套全局路由。

- 一个窗口同一时刻只有一个主场景；浮层（审批、问卷、命令面板）是场景上的显式焦点栈，不改变底层会话归属。
- 焦点栈记录「谁在接收按键」；失焦的视图不能收到输入，也不能把草稿写进别的会话。
- 功能注册是静态的、显式的贡献：功能声明自己的场景、命令入口、按键和可见条件；不引入运行时动态插件发现。
- 场景切换按地址保存/恢复草稿、阅读锚点和流式接收；S03 的阅读位置和 S12 的子草稿通过地址挂接，不复制会话状态。切换后当前视图只显示新地址的数据，旧地址内容不残留在新场景。

## 7. 失败与不变量

1. 官方消息、工具结果和队列事实不被本地状态覆盖；重连以官方为真源。
2. 没有官方回执的提交不显示「已发送」；没有持久事件的助手内容不进入历史。
3. 已知 attempt 的 revision/dense-index/settlement 缺口才重开 follow；未知 attempt 的 live 帧忽略，持久结算照常发布，不拼接、不猜字段。
4. 空白提交、未就绪附件、宿主未就绪都明确拒绝并保留草稿；归档 Gate 和 writer-held 分别由 S03/S01 处理，S02 不伪造这两类检查。
5. 失败、审批和中断状态不能被折叠动作藏掉；S03 可以降噪，但不能改写事实。
6. 本地回显和预览必须有界；慢消费者不能阻塞官方持久化，也不能无限缓存。
7. 退出时先停止接收新提交，再取消活动回合，最后排空展示层；不把「界面关闭」当成「后台已停」。
8. 所有消息、回显、队列、附件、预览和草稿按地址归属；任何内容不跨会话、父子地址或场景出现。
9. 合成 bash 记录不是用户消息，也不是审批授权；Agent/Monitor 不能据此跳过审批、改变策略或重置预算。

## 8. 验收

- [ ] 用真实官方会话完成一次文本发送、流式接收、工具调用和正式消息落历史；刷新后从官方记录重建，不依赖本地缓存。
- [ ] 多行、括号粘贴、中文输入法组合态、超长单行均不丢字、不误发；复制得到原文。
- [ ] 运行中默认 queue、显式 steer、删除队列项、停止保留队列符合官方 inbox 事实；「停止并清空」按逐项删除 + cancel 的竞态说明验证。
- [ ] 已入队/已落盘的 `requestId` 重复提交不产生第二条消息；claim 窗口/子代理路径的结果未知不会被自动重发。
- [ ] 断线、重连、旧 generation 事件、已知 attempt 缺口均不制造重复消息或错位归属；未知 attempt 不触发反复重连。
- [ ] 切换会话、进入子对话再返回，草稿与焦点恢复，消息仍来自各自官方地址。
- [ ] 切换地址后，transcript、回显、队列、附件、草稿、预览都不出现上一个地址的内容。
- [ ] 空白提交、附件未就绪、宿主未就绪三种拒绝保留草稿并给出可区分原因；归档 Gate 与 writer-held 由 S01/S03 验收覆盖。
- [ ] 本份的协议夹具、真实会话记录和失败注入证据随交付提供；真实会话记录必须脱敏或取得用户授权。

## 9. 机制清单

| 机制 | 解决什么 / 没有会怎样 | 确认与代价 |
| --- | --- | --- |
| 本地提交回显 + `requestId` | 用户点击后立即看到自己的消息，又不伪造历史；没有则界面卡住或重复消息 | 作者建议；回显只存展示内存，重连即失效 |
| 官方消息/工具身份映射 | 用户消息主键是 `user/message.seq`，`source.rpcId` 只在 `user-rpc` 源上；工具用 `callId`，结果用 V4 顶层 `toolCallId` | 官方契约；字段名必须写清 |
| 有序输入内容列表 | 文本与附件保持用户顺序；没有则提交顺序和预览不一致 | 作者建议；S06 产生附件 |
| 命令入口与路由 | `/` 命令、技能、`!` 各有 owner；没有则 S02 解析错业务 | D02 契约；S02 只路由 |
| 流式预览与持久消息合并 | 预览不是历史，正式消息替换；没有则失败 attempt 留在历史 | 官方 attempt 语义；需处理 `assistant/attempt` |
| 队列/插话分义 | 区分 queue 与 steer；没有则用户无法预期消息何时进入模型 | 官方两种 delivery mode；steer 是 best-effort |
| 停止保留队列 | 停止生成不误删已排内容；没有则一次 Esc 丢光后续输入 | 公开 cancel 硬编码 keepInbox；清空需逐项删除 |
| 按地址保存草稿 | 主会话与子对话互不串稿；没有则切换会话丢输入或写错会话 | D02 契约；只存在进程内 |
| 跨地址内容隔离 | 任何 transcript/回显/队列/附件/草稿不跨会话；没有则串内容 | 用户硬要求；需在验收逐项覆盖 |
| 统一场景/焦点/注册接口 | 避免每个功能私改全局路由；没有则按键和会话归属互相踩踏 | 总纲已定；S02 独占该接口 |

## 10. 自定细节

- 运行中默认排队、显式插话的按键由 S02 自己定义，但最终键位统一由 S13 的 design-contract 冻结；S02 不拥有整张键位表。
- 公开 cancel 硬编码 `keepInbox: true`；「停止并清空」只能是逐项删除队列 + cancel 的复合动作。被 claim 的项返回 `session/queue-item-not-found` 时重读队列并显示剩余项；不能声称是原子官方接口。
- `bash-mode` 是 Nano 本地显示标记，不是官方 `MessageSource`；注入走官方 `inject` 的 UserMessage。运行中 Agent 在最近 step boundary 取走，空闲 Agent 等下一次 follow-up/steering。
- 编辑带附件的队列项一律禁止：官方 edit 只接受 `TextBlock[]` 且整体替换，没有只移除附件的队列动作。
- 草稿只按会话地址保存在内存，不跨进程恢复，不写入官方存储。
- 有序输入列表由 S02 定形状，附件上传回执由 S06 产生；S02 不定义图片格式与大小上限。
- 场景/焦点/功能注册接口的具体 Rust 类型由 S02 定义，其他子件只消费；新增全局路由引用须经 S02 工作区唯一变更。
- 初始输入上限、回显保留条数和预览合并窗口由本份实现时按实测定，不在规格里先写死数字。
