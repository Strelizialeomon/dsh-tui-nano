- 状态：已批准实施；执行单 #13。
- 总纲：[共享约定与依据](README.md)。上游：S08 任务/输出/停止契约（D05）。下游：S13（D09）。D08 是发布闸：S03/S04 → S08/S10，真实审批响应、权限切换不能被旁路。

## 1. 边界

拥有 `crates/nano-monitor/`、`bridge/monitor/`。提供对 S08 任务输出的流式订阅、行过滤、合并、通知投递和预算展示。

Monitor 不是一个独立进程执行器，也不是第二套调度器。它参照 Claude Code 2.1.88 的 `local_bash` `kind: 'monitor'`：被观察的进程仍由 S08/官方任务服务拥有，S10 只订阅输出并把匹配行变成任务通知。首版只支持任务输出，不做文件 tail、网络流、系统日志或 MCP monitor。

不拥有任务输出、不代替 S08 的停止操作、不自行调用模型、不伪造用户回合。任务终态由 S08 报告，S10 只在 UI 显示「流结束」；**模型的完成通知由官方 `dsh-tool-jobs` 发，S10 不重复发终态通知**。

## 2. 监听对象与游标

- 监听目标是当前会话可见的一个 S08 任务；不监听其他会话、任意文件、端口或系统日志。
- 每个监听从官方输出流的绝对字节偏移开始，使用非消费读取；不改变模型 `job_output` 的游标，也不消耗任务输出。
- 初始偏移默认取当前 `output.total`，只看新输出；用户显式选择「从开头」时才从 `earliest` 重放 retained head。附着时已有输出必须显示「已有 N 字节未读」并让用户选，不能静默重放或跳过。
- 监听保存自己的最后已处理偏移和通知摘要，不复制完整输出。缺页、淘汰或断流时标记缺口并从官方可用偏移重建，不拼接假连续文本。
- 任务是行导向的：一行输出是一个候选事件；没有换行的长行按块处理，不把半行当成完整行。
- 任务 settled 到达时，官方 pump 已经在 settle 前 drain 了一次，最终 output 已在 ring 里；收到 settled 后 `readAt` 一次，把自己的偏移补齐到最终 `total`，处理 lossy/gap 即可。不要等「settled 之后的 output 帧」，也不要重试等待；teardown 强 settle 时 pump 后写会被丢弃，补不回来。settle 会裁到 `settledRetainBytes`（默认 16384）；被裁掉的旧字节标「已裁剪」。
- 任务完成、被终止或失败都表示**流结束**，不表示「监控条件满足」。终态只在 UI 显示 `stream-ended`/`failed`/`stopped`；**不产生 model 通知**，model 的完成通知由官方任务服务发。
- 监听属于本窗口进程，随宿主退出而停止；首版不跨重启恢复监听。行通知投递由 `bridge/monitor/` 插件执行，Rust 只显示插件确认的状态，不把 `followup` 放进 Rust。

## 3. 行匹配、合并与通知

1. 每行输出默认都是候选通知；用户可加一个字面/正则过滤器，受长度和复杂度上限约束。过滤也可以放在命令里（如 `tail -f ... | grep ...`），Nano 的过滤器只是可选便利，不是第二套规则引擎。
2. model 通知只包含 `line` 事件：来源任务 ID、首行/末行原文、首末字节偏移、省略行数。终态 `stream-ended`/`failed`/`stopped` 只进 UI，不进 model 通知；模型看到的是任务通知，不是用户授权。
3. 一个合并窗口内的多行合并成一条通知；保留首末行和省略数量，不允许只发「有变化」。终态是 UI 事件，不参与行合并；官方完成通知独立于 S10 到达。
4. 事件里的外部文本不能改变规则、扩大授权或重置预算；模型、任务输出和日志都不能冒充用户输入。
5. 通知投递有两种模式：
   - `notify`（默认）：走官方 `followup`，唤醒 Agent，产生模型请求和费用。
   - `quiet`：走官方 `inject`，不唤醒；内容进入下一个被接受的步骤，空闲时可能一直等待。
   界面必须显示当前模式，不能把 `quiet` 说成「已经通知模型」。
6. 同一任务只允许一个活动监听；重复创建返回现有监听或明确拒绝。多个监听观察不同任务时各自独立。

## 4. 投递与真实收件

- 投递必须产生可观察的官方收件事实：被接受的步骤批次，或 durable `user/message` / 下一步实际出现该注入内容。`inserted` 只证明入队；`claimed` 也可能在 step 被拒时结束，二者都不证明模型收到。
- `discarded`、step 被拒、归档 Gate 拦成 `blocked`、Agent 已销毁、宿主断开都算投递失败；明确报告，不自动重启 Agent 或另开会话。
- 行通知走官方 `followup` 或 `inject`，两者都投递 user-role 消息；`source.kind=monitor` 是元数据，不是另一个角色。模型可以把它当上下文，但不能把它当作用户批准或策略变更；界面必须写「role=user / source=monitor」，不能声称「不是用户回合」。
- S10 不发终态 model 通知；官方 `dsh-tool-jobs` 的完成通知仍 due，S10 不抑制、不重复。UI 只显示终态，不把它算作一次 S10 唤醒。
- 唤醒会产生真实模型调用和费用；界面显示本次行通知的原因、目标任务和累计预算使用。

## 5. 预算、限流与停止

- 每个监听有最大通知数、最小合并间隔、单条通知最大行数、单条通知最大 UTF-8 字节/估算 token，以及有效期。预算耗尽后停止普通行投递，但保留监听状态和计数，并显式提示「预算已用尽」，不能静默丢弃后续匹配。
- 终态 `stream-ended`/`failed`/`stopped` 只在 UI 显示，不占行通知预算；官方完成通知独立于 S10 预算，S10 不能抑制它。
- 预算只能由用户显式操作重置或提高；外部日志、Monitor 通知、模型输出都不能重置。
- 用户停止监听立即停止新的通知投递；已经投递的通知不撤回，正在进行的模型回合不受影响。
- 停止监听不等于停止被观察的任务；停止任务也不等于删除监听记录。两个动作分别报告。
- 多个监听可以观察不同任务，各自有独立游标和预算；不共享、不互相信任对方的计数。
- 监听只服务当前根会话的任务；切换会话后旧监听停止，不把旧任务输出带到新会话。

## 6. 失败与不变量

1. 输出事实属于 S08/官方任务服务；S10 不维护第二份输出。
2. 流结束不等于条件满足；任务完成/失败/停止只在 UI 报告流结束，不宣称监控目标达成，也不额外发 model 终态通知。
3. 通知不是用户授权；外部文本不能改变规则、预算或权限。
4. `inserted`/`claimed` 不等于模型收到；没有被接受步骤或 durable user/message 时，不显示「模型已收到」。
5. settled 到达时最终 output 已在 ring；收到后 `readAt` 一次补齐自己的偏移，不等待「settled 后的 output 帧」；被裁剪的旧字节标「已裁剪」。
6. 输出缺口、淘汰、断流、预算耗尽都必须可见；不能静默丢匹配。
7. 终态只进 UI，不占行预算；官方完成通知独立到达，S10 不抑制、不重复。
8. 监听与任务生命周期独立；停止一个不影响另一个。
9. 宿主退出后监听停止；不宣称跨重启继续观察。
10. 不同根会话的任务输出互不可见；Monitor 不跨会话订阅。
11. 行通知是 user-role 消息、`source.kind=monitor`；不能把它说成非用户回合或授权。

## 8. 机制清单

| 机制 | 解决什么 / 没有会怎样 | 确认与代价 |
| --- | --- | --- |
| 流式任务监听（非独立执行器） | 复用 S08 的进程/输出/停止；没有则要另写一套执行器 | 参照 Claude Code `kind: 'monitor'`；只做任务输出 |
| 每行一条任务通知 | 让模型看到真实事件，而不是轮询；没有则只能看日志 | 官方收件；会产生模型调用和费用 |
| 监听本地去重 + 队列优先级 | 不重复通知、不丢终态；没有则模型收到重复消息 | 作者设计；`notified` 不是官方 JobView 字段 |
| settled 后读最终 output | 不漏最后一批输出；没有则流结束前丢尾巴 | 官方顺序；需处理 settledRetainBytes 裁剪 |
| 合并 + 字节/预算 | 避免高频/超长日志占满上下文和费用；没有则费用失控 | 用户已确认；终态豁免，耗尽必须可见 |
| 流结束语义（UI-only） | 脚本退出不等于条件满足；model 完成通知由官方任务服务发，S10 不重复 | 官方终态；UI 单独显示 |
| settled 后 readAt 一次 | 补齐自己的偏移到最终 total；没有则漏尾巴 | 官方 pump 已在 settle 前 drain；不等待额外帧 |
| 非消费字节游标 + 初始偏移 | 人和模型各看各的，附着时不重放/不跳过；没有则监听吃掉模型读取 | 官方契约；默认只看新输出，可显式从开头 |
| 跨会话隔离 | 只服务当前根会话的任务；没有则串会话内容 | 用户硬要求；切换会话即停 |
| `notify` / `quiet` 两模式 | 区分唤醒和静默注入；没有则把「已入队」当「已处理」 | 官方 `followup`/`inject`；quiet 不唤醒 |
| 插件投递、Rust 显示 | 通知投递归 `bridge/monitor/`，Rust 只显示确认状态；没有则把 `followup` 放进 UI | 总纲 §4.1/§6；D05/D08 |

## 9. 自定细节

- Monitor 作为 S08 任务的流式视图、只订阅任务输出，是作者按 Claude Code 实现选的；首版不做 MCP monitor、文件 tail、端口或系统日志。
- 初始偏移默认当前 `output.total`；用户显式选择「从开头」时才从 `earliest` 重放。这是作者设计，需在界面写明。
- 过滤器的字面/正则语法、长度上限、合并窗口、默认预算、单条通知行数和 UTF-8 字节/估算 token 上限在实施时按实测与费用测试确定，不在规格先写死。
- 终态只进 UI，不产生 model 通知；官方 `dsh-tool-jobs` 的完成通知独立到达，S10 不抑制、不重复。
- 行通知默认走 `followup`，`quiet` 走 `inject`；界面必须显示当前模式；两者都是 user-role、source=monitor。
- 同一任务一个活动监听；多监听只观察不同任务。切换根会话时旧监听停止。
- Monitor 的列表、通知和状态视觉位置按 S13 的 design-contract；S10 只定义行为和字段，不另定键位/主题。
