底部增加 Subagent Dock：最多直接展示 4 个 subagent，多余折叠；状态灯为执行中闪烁、错误红色、终止黄色、完成绿色。输入框为空且无更高优先级交互时，上下键进入 dock；点击/Space 打开主会话内 Peek，Enter/→ Attach 到完整交互会话，Esc 关闭 Peek/返回 dock。

## Latest correction: Claude-style Peek / Attach

之前把“选中 subagent”直接设计成只读全屏 `AgentTranscriptScene` 是错误的。Claude Code 的实际交互是：点击/Space 打开主会话内 Peek panel，显示最近输出/等待状态并可直接回复；Enter/→ 才 Attach 到完整交互会话。规格和样稿已改为两级模型。

回答与关键结论要容易扫描；用粗体、亮度、留白、缩进形成主次，兼顾终端统一字号的现实。
2. **执行过程降噪**：思考默认单行；Bash 命令默认 1 个可视行，运行输出 2 个可视行；完整内容按需查看。用户已在选项卡中确认这组规则与滚轮统一一起纳入首版。
3. **少 emoji、少动效**：应用自带装饰性 emoji 尽可能少，默认方向为不显示；完成记录静止，保留必要状态与少量功能符号。不要删改用户原文、代码或日志里的字符。
4. **代码变更借鉴 Claude Code**：文件名、准确增删统计、真实行号、红绿整行底色与行内变化强调构成独立代码块；窄屏也要清楚。

6. **整块快速开关**：代码与 Bash 的命令、代码、预览输出、展开正文都可单击展开，再点收起。用户明确反对仅点击标题，以及按网页思路增加小按钮；原位开关、无过渡动画，拖选/复制不误收起，普通助手正文不跟着折叠。
7. **明确删除两项功能**：不增加“复制修改后代码”和“展开原始差异”按钮或工作流。保留已有文本选择与复制能力，展开后仍是同一个差异块。
8. **选项交互参考 pi-plugins**：单列编号，焦点与已选分开；单选 Enter/数字直选，多选空格勾选且 Enter 不暗加焦点项；Other 行内输入，多题可回看并整体提交。
9. **授权不是新增流程**：样稿里的“等待确认”只用于演示原有后端权限请求。不会让每条 Bash 都弹确认；先说明动作和实际原因，可选项、默认拒绝、长期授权及快捷键限制仍遵循后端。
10. **滚动从项目层面解决**：统一正文、底栏、侧栏的输入规则，处理反向与容器切换，保持阅读锚点；不能仅靠安装目录补丁或继续盲调数字。
11. **底部与上下文**：默认底部只保留权限/安全状态、运行或错误瞬态和工作目录；模型、上下文数字、缓存、成本、Token、`Ctrl+O` 不常驻。上下文容量通过输入框上下边框同步色段表达，精确数据从 `/tokens`、`/status` 查看。

## 目标与已确认范围

默认界面应让用户先看清回答和需处理事项，再按需查看执行细节。界面尽可能少用 emoji；正文、代码变更和工具过程各有清楚的层级。滚轮行为在正文、底栏和侧栏保持一致，用户阅读旧内容时位置稳定。

用户已确认纳入三项规则：M1 思考默认单行并可展开；M2 命令一行、运行输出两行；M3 统一滚轮入口与反向行为。随后追加：代码编辑块借鉴 Claude Code；长变更折叠；代码与 Bash 整块单击开关；删除额外的代码复制/原始差异按钮；问卷和确认选择参考 pi-plugins 选项卡。

首版交付：

- 阅读层级、少装饰与一致状态文案。
- 思考、命令和工具结果的有界默认展示，保留原始记录与详情。
- 代码差异的独立呈现、长内容折叠、整块快捷开关，以及真实来源的行号、统计、应用状态。
- pi-plugins 风格的普通问卷与授权选择，保留后端支持范围与真实答案契约。
- 统一滚轮输入、速度设置、反向与目标切换规则，保护阅读锚点。
- 相应回归与中英文用户文档同步。

后续可选：整轮工具汇总、只保留最终回答的 Focus 视图、专用实时调速面板、自动弹出的 Git diff 侧栏。本规格不要求这些功能，不重做 Agent、工具执行、权限或持久化域，不调整模型是否思考。

本机内存输出探针的渲染区间 p95 约 2.24ms/2.28ms（100/60 列），不含真实终端显示，也不完整包含提交前工作。因此不据此承诺 60fps 或整个应用没有性能问题。

## 阅读与装饰约束

1. 沿用终端字号与项目主题系统。正文使用正常文字色；小标题、原文强调使用粗体；段落间留一行，相关状态紧靠对应内容。
2. 继续呈现后端提供的 Markdown，不依据自然语言猜测最终回答，不删除面向用户的助手文本。中立事件目前没有统一的 `commentary/final` 字段。
3. 应用自带装饰性 emoji 默认不出现。提问、折叠与必要状态使用少量固定文本符号，状态同时有文字；原文、代码、日志中的 emoji 不过滤。
4. 已完成记录保持静态。默认主会话最多一处持续忙碌指示，使用单色字符；其他任务通过状态、用时或真实进度表达活跃情况。
5. 错误与警告保留状态色；去色环境仍能凭文字和符号识别。增删代码的红绿属于内容语义，不受去装饰规则影响。
6. 保留必要权限模式、模型与上下文信息，不以简化为由覆盖用户已有状态栏字段选择。静态简短标题成为未显式设置的默认开屏方向。
7. 明暗主题都必须可读；常规文本对比度以 4.5:1 为检查目标。实际终端底色、ANSI 降级与用户主题分别验证，不把浏览器色值直接视为生产契约。

## M1：思考的默认展示

- 未显式设置时，思考正文默认折叠为一行状态与已有用时/计数；流式阶段保持稳定高度。
- 点击单条或使用现有全局详情入口可查看后端实际提供的正文。只有 token 计数时，只显示计数，不提供虚假的全文入口。
- 单条主动展开在该条完成后仍保留；其他消息更新不会替用户收起。全局详情与单条状态的关系沿用现有约定并覆盖回归。
- 取消、失败与历史回放使用真实状态；未知用时不编造。折叠只改变视图，不删除思考记录或改变模型请求。
- 显式选用现有全文/预览显示的用户偏好继续有效；默认更新不自动覆盖它们。

## M2：命令与输出的可视行预算

“可视行”指按当前可用终端宽度排出的行，计入 CJK、组合字符、ANSI、缩进和状态栏位的实际宽度。

| 内容 | 紧凑态要求 | 详情与例外 |
| --- | --- | --- |
| 命令标题 | 1 个可视行；状态与隐藏内容提示可辨认 | 单条展开完整命令；超长单行同样受预算约束 |
| 运行输出 | 最新 2 个可视行，原位更新 | 显示省略事实，详情保留已有可用输出 |
| 已完成输出 | 1 条有依据的摘要或退出状态 | 无可靠摘要时显示状态/输出规模；不调用模型补摘要 |
| 失败 | 失败状态、退出码/信号及错误摘要在折叠外可见 | 完整错误可展开，错误不能被成功摘要遮蔽 |
| 审批 | 仅收到后端权限请求时出现，说明动作与已有授权原因，完整命令可滚动核对 | 复用既有审批语义，不新增每条 Bash 必须批准的步骤 |

- 完整命令与结果仍由后端和既有会话记录拥有。当前接口确实只有截断结果时，应注明可用范围，不能把预览当成完整记录。
- 保留整块点击与 Ctrl+O 等现有入口：在鼠标捕获模式，Bash 的命令、预览输出和展开正文均可单击展开，再单击收起，不能限定为标题或小按钮。展开/收起在释放单击的同一交互周期完成，不添加过渡动画或额外确认。
- 拖选、文本选区、复制和专用链接操作优先，不能被卡片开关抢走；卡片外空白与助手普通正文不误触。键盘详情和 inline 的原生终端选择路径继续可用。
- 展开后的长内容继续使用有界渲染，不能为了“全文”一次挂载无界行数。
- 用户主动展开的记录保持展开；停止和失败必须立即呈现，不能等待文字动画完成。
- Bash/PowerShell 与普通文本结果共享规则；代码差异使用下节的独立预算，不能压成一行日志。

## 代码变更块

本节复用现有 `ToolFileDiff`、patch 解析、双栏对齐、语法高亮与主题角色，统一窄屏和宽屏的呈现，不新增差异数据真源。

### 信息结构

- 首行清楚显示工具/操作、文件路径、实际增删统计；路径过长时有可访问的完整路径。
- 待执行时标“修改预览 / 尚未应用”；收到成功结果后才能标“已应用”。失败、拒绝或取消不使用成功状态。
- 修改代码置于与普通正文明确分开的区域，可用轻分隔线、固定行号栏和语义底色。保持字号一致，不添加装饰性图标。
- 上下文行保持中性；删除行有红色系整行底色，新增行有绿色系整行底色；`-` / `+` 标记始终保留。
- 能可靠配对的替换行进一步强调真正变化的片段，保留其余代码的正常可读性。无法可靠配对时只使用行级差异，不编造词级关系。
- 语法高亮可保留，但不能盖掉增删语义。选中、悬停与展开状态下仍能辨认改动；纯装饰背景关闭不应关闭差异底色。

### 数据与宽度约束

- patch 提供的行号按旧/新文件坐标准确显示；只有 old/new 片段且无文件偏移时，行号栏留空或省略。不能给未知偏移假造文件行号。
- 新建、删除、重命名、多文件和多段修改分别保留对应身份与统计。补丁无法解析时明确回退到原始内容，不伪造增删数量。
- 首版保持现有 `auto/split/unified` 设置与自动双栏门槛。常见窄屏统一差异也具备行背景和行内强调；宽屏复用既有双栏能力。
- 默认差异代码区最多 8 个可视行，换行续行、文件/修改段分隔共用预算，不能每段重新获得 8 行。短改动直接显示，长改动优先保留第一处可理解的完整变更及少量上下文，并提示尚未显示的范围；不能把一整屏预算花在无改动上下文上。
- 可在不超过预算时保留一对增删内容；跨段裁剪不能造成错误的相邻关系。无法低成本精确计数时显示“更多变更”，不编造数量。超长单行也受可视行上限约束，并在昂贵高亮/布局前采用已有的有界处理方式。
- 代码变更与 Bash 使用相同开关：单击代码块内容区域展开，再单击该块内容收起；标题只是同一块的一部分。展开后仍是同一差异视图，位置稳定；保留既有全局详情入口。
- 按用户要求，不新增“复制修改后代码”和“展开原始差异”功能或按钮。保留既有文本选择、复制与原始记录能力；拖选不切换折叠，单条主动展开不被新消息自动收起。
- 展开内容仍应按有界工作量渲染，并可随转录浏览；不能一次布局数千行。换行续行不重复假行号，实际只持有截断数据时明确说明可用范围。
- 文本中包含文件路径并不等于它是代码变更；只将后端确认的差异呈现为修改记录。

## 选项卡：参考 pi-plugins

适用于普通模型问卷与后端授权选择。模型列表、设置列表、`/provider` 专用编辑器、密钥输入及计划审批的专用正文不机械替换为通用问卷；既有专门能力保留。

### 布局和选择

- 单列排列，标签和说明分行。编号、焦点指针、勾选标记各有职责；初始焦点不等于用户已经作答。
- 当前焦点使用强调色，已选项有文字标记和稳定选中色。移动焦点不改变已选项，也不因焦点变化插入空行而让列表跳动。
- 单选 Enter 或允许的数字键直接确认当前项；鼠标点击整条选项也可确认，不增加第二层网页式按钮。
- 多选 Space/数字键切换勾选，Enter 只确认已勾选项，不能暗中选入当前焦点。空答案显示就地错误并保持打开。
- Other 在列表末尾行内输入；焦点位于输入时，数字、空格、普通字母属于正文，不触发选项快捷键。沿用本项目可靠的终端输入、粘贴、IME 与秘密字段保护，不能复制 Pi 的专有编辑器依赖。
- 多题按题签横向切换；每题独立保存选择和草稿；Tab/左右键不隐式确认。普通多题问卷最后进入整体提交屏，可回看、定位未答题并一次提交；单题保持直接提交。
- 提交后以真实结果显示一行一题的回执；取消、后端中止和未回答不得显示为已回答。

### 高度与宿主能力

- 卡片使用本项目已有挂载与焦点层级，不引入 Pi 的浮层栈或抢走转录已有滚动能力。根据 `useTerminalSize()` 与实际剩余空间计算预算。
- 选项窗口以 5 项为初始上限，并随可用高度收窄；焦点移出时窗口跟随。长题目和说明有明确裁剪提示，使用普通文字“另有 N 行未显示”，不引入剪刀 emoji。
- 题签宽度不足时压缩为短标签/当前题；操作提示与有效选择入口不能被正文挤掉。卡片裁剪不能改写提交的原始答案。
- 原请求的选项数量、ID 和后端限制保持；不把 Pi 的工具参数上限套到所有现有本地向导。
- 首版保留 `selected/custom` 结果语义。Pi 的独立 Notes 与 Chat about this 无对应结果通道时不展示空入口，不把“先讨论”伪装成提交答案或授权。
- 普通问卷 Esc 取消整批，后台中止及时释放焦点与队列；既有手动收起入口保留，不因换皮删除。

### 授权卡

授权卡共用编号、焦点、说明与键盘提示的视觉语言，选择集合仍来自后端。DSH 的两项保持允许一次/拒绝；不增加 Other、先讨论或始终允许。其他后端提供长期授权、反馈、默认拒绝或限制数字快捷键时，仍按其原有契约执行。

只有后端提出权限请求才显示授权卡。优先说明要执行的动作与后端给出的原因；没有具体原因时如实写明后端请求确认，不能自行推断风险或制造新审批。命令完整内容可通过既有滚动查看，拒绝和取消仍按原规则返回。

## M3：滚轮输入与阅读位置

### 统一处理

- 原始滚轮输入只归一化一次，再按位置与模态优先级投递。正文命中路径、底栏回退与侧栏不能各自重新乘倍率。
- 相同输入、配置、初始位置和可滚动空间下，各入口得到相同位移语义。到边界时允许钳制；无目标或弹窗覆盖时遵循既有阻止穿透规则。
- 速度与加速由同一处设置规则决定。复用现有 `/settings`，支持有限正数及小数速度，拒绝 NaN、Infinity 与无效值；遵循现有配置优先级。
- 小数余量按明确的手势/目标边界累计，再以整数行交给现有渲染器；不能把正负小数直接分别 `floor` 造成方向不对称。
- 反向立即清理前一方向的加速与不合适的未消费位移。切换滚动容器不携带上一容器的余量或加速；横纵轴互不污染。
- 同批事件不丢失、不重复；批次边界不重置位移累计。不能把小于某个处理间隔当作可靠的物理刻度识别。
- 使用已有待滚动位移与分帧绘制机制，不通过丢弃已接受的整数位移给吞吐硬封顶。大位移仍受视口与实际边界约束。

### 跟随与锚点

- 上滚后暂停跟随新内容，用户主动回到底部才恢复。生成结束、思考折叠和工具结果到达不能抢走阅读位置。
- 折叠、展开、重测高度、宽度变化时，保持可识别的消息/内容锚点；尺寸变化不能留下空白区或使末行不可达。
- 显式跳转、分页与回到底部不是滚轮手势，不继承滚轮加速状态。
- 不把网页版像素滚动作为终端整行滚动的验收依据。

### 旧补丁与兼容

本机旧方案修改 profile 的 `App.js`，并有 `ensure.sh` 在启动前补回。新源码能力必须覆盖这套用户需求，并在临时安装 fixture 中验证已知旧补丁不会再次给新规则叠加倍率。

复用的旧变量或迁移策略必须在实现文档中写清优先级、有效范围与退出条件；不静默改写用户 shell 文件或其他项目。新版本代码结构不应继续命中旧的固定 `±3` 替换模板。插件无法安全识别新结构时，应保持产品代码并给出明确提示。

## 1. 六个方面，统一成克制的阅读体验

| 用户感受 | 本次核实的情况 | 建议方向 |
| --- | --- | --- |
| 内容看起来一样，找不到重点 | 已有标题、粗体、主题色，但回答、工具、过程在同一条信息流竞争注意力 | 统一信息层级，让回答和待处理事项最醒目 |

| 滚动不跟手 | 补丁已生效，但正文与底栏走不同速度规则；加速受事件批次与方向历史影响 | 将滚动策略纳入源码，统一路由、手势状态与设置 |

这些要求会相互影响：展开的大脚本和长差异增加滚动距离，内容不断增长和收缩会改变位置，动态图标和预览又持续吸引视线；选择卡还需要稳定的焦点与尺寸。因此需要共同设计展示规则、注意力分配与阅读位置的稳定性。

## 2. 内容层级：颜色已经存在，主次仍需要统一

当前源码并非所有文字都同色：

- 用户提问使用加粗和主题强调色。
- Markdown 一级标题有加粗、下划线和强调色，二级标题有另一种强调色；普通粗体也会呈现。
- 思考使用弱化文字；工具按类别着色；退出失败会显示错误色。
- 助手正文主要依靠传入 Markdown 决定层级，TUI 不会自动理解哪一句是结论。

因此，“一眼抓不到重点”是有效的体验反馈，但还不能直接归因为颜色功能失效。当前终端环境确认为 Ghostty，并声明 truecolor；尚未对用户正在看的那一屏进行视觉采样，不能排除具体主题、内容格式或设置的影响。

**建议采用少量、固定的视觉职责：**

| 信息 | 默认呈现 | 目的 |
| --- | --- | --- |
| 回答、结论 | 正常高对比正文，重点加粗，段落留白 | 第一眼能开始阅读 |
| 你的问题 | 固定前缀与强调色，与回答留出间隔 | 快速定位每轮起点 |
| 运行过程 | 次一级亮度，一行状态或少量汇总 | 知道还在工作 |
| 脚本、参数、完整日志 | 折叠后按需查看 | 保留排查能力 |
| 错误、等待回答、审批 | 明确文字与标记，必要时强调色 | 不被折叠淹没 |

在当前字符网格渲染架构下，字号由终端统一控制，文本组件也没有局部字号接口。可移植的主要手段是粗细、亮度、间隔和缩进。特殊终端的文字缩放能力可以另行研究，但不应成为第一轮改进的前置条件。

另外，中立事件目前区分文本、思考和工具，但没有统一的 `commentary/final` 字段。第一轮可以保留全部面向用户的助手文字，先收起工具与思考。若要进一步实现“只保留最终回答”，应先明确三种后端的回合结束与回答归属，不能靠关键词猜测并隐藏助手内容。

### 符号与动效：尽可能少用 emoji

用户已明确要求减少 emoji、让视觉更克制。建议把它作为整个界面的共同约束，覆盖聊天记录、工具卡、思考块、子任务、状态栏与开屏。以下具体数量与默认行为是我的建议，尚未定稿为规格。

本次补查的事实：

- 思考块结束后显示锚形标记；运行中有每 80ms 更新的旋转符号及颜色脉动。
- 子任务完成、失败、未知等状态使用彩色圆球 emoji；普通后台任务已有文本符号，两个入口并不统一。
- 活动动画默认选 `moon8`；本机实际依赖中，它包含 8 个 emoji 帧，每 120ms 切换。已有 `dots` 预设使用普通字符，可以作为复用起点；其 140ms 节奏也仍需按克制目标调整。
- 现有“极简界面”只覆盖部分装饰。运行中的子任务仍直接取活动预设，未统一切到普通字符；底栏还会覆盖已保存的字段偏好。设置说明写“只留模型与目录”，但实际常量保留默认指标并关闭部分装饰，不能仅按说明推断效果。

**推荐的统一规则：**

| 元素 | 推荐默认 | 保留的作用 |
| --- | --- | --- |
| 自有界面的装饰性 emoji | 默认 0 个；去掉锚、月相和彩色圆球等装饰 | 用明确文字表达思考和任务状态 |
| 结构与操作符号 | 复用少量单色标记，如 `>`、`▸`、`✓`、`×`；同一含义只用一种 | 定位提问、折叠、完成与失败 |
| 忙碌动画 | 主会话默认集中在 1 处低频指示；并发任务用文字状态和用时 | 明确还在工作，避免多处同时跳动 |
| 颜色 | 正文与次要文字分层；少量强调色用于交互，错误和警告有明确状态色 | 主次清楚，状态不依赖颜色单独表达 |
| 开屏装饰 | 默认静态简短标题；吉祥物、随机样式和装饰动画作为用户主动选择 | 保留品牌识别，减少启动噪声 |
| 已完成的过程 | 静态、低强调摘要，保留展开入口 | 阅读回答时不持续争夺注意力 |

去掉装饰时保留必要的运行、错误、权限模式与上下文信息，不把“少 emoji”捆绑成删除功能或关闭所有层级色。现有开关可复用的部分应核实后采用；没有必要先增加一套主题或图标框架。

约束首先作用于应用自己的界面文案与图标。助手新回复可通过输出风格约定减少装饰性 emoji；不要在渲染时删除用户原文、代码、工具日志或已有消息里的字符，以免改变内容与复制结果。

减少动画的直接收益是减少视觉干扰；能降低多少渲染负担仍需测量，不能把移除 emoji 当成滚动性能修复的证明。

## 3. Bash 与 thinking：统一默认展示预算

本次从源码核实的默认行为：

| 内容 | 当前行为 | 对体验的影响 |
| --- | --- | --- |
| 普通 Bash / PowerShell 命令 | `foldTerminalCommand=false`，多行脚本可作为标题完整换行 | 输出已折叠，命令本身仍可能占满一屏 |
| 运行中的工具输出 | 全屏最多 8 行，inline 最多 5 行，另外有状态与省略提示 | 一张运行卡仍占较多纵向空间 |
| 已结束工具输出 | 通常保留 3 个源文本行，之后给出折叠提示 | 长源文本行还可能换成多行显示 |
| 思考过程 | 默认标题 + 3 行动态预览，结束后折叠 | 有持续变化的视觉噪声，结束时高度改变 |
| 后台任务 | 已有连续任务分组与折叠 | 普通前台工具还没有同样统一的每轮汇总 |
| 全局详情 | `Ctrl+O` 展开思考和工具内容 | 查看一个细节时，可能让整段记录变长 |

**我的推荐默认值是以下方向，具体行数属于待确认建议：**

- thinking：默认只留“正在思考 / 思考完成 · 用时”一行；点击查看全文。这里的折叠只改变呈现，不改变模型是否思考。
- Bash：默认一行说明或有界命令预览，并显示运行/成功/失败状态。普通运行输出可控制在 1–2 个可视行，完整脚本和日志按需展开。
- 连续成功工具：首版保留逐条记录与单独展开。后续可选再合为“读了几个文件、运行了几条命令”的一行记录；用户主动展开的项目保持展开。
- 失败和需处理事项：保留可见原因与状态。审批面板仍须显示审批所需的实际命令，不能被聊天记录的简洁规则带着一起隐藏。
- 执行摘要尽量从已有工具名称、路径、状态、退出码、计数生成，不额外调用模型编写摘要。

展示示意如下，数字和文案只是样例：

```text
> 帮我找出构建失败的原因

  ▸ 思考完成 · 4s
  ▸ Read 配置读取入口 · 完成
  ▸ Bash 检查命令 · 失败     [展开脚本与日志]
  构建失败：缺少配置项

原因是启动配置缺少 API 地址。

需要修改
给本地配置补上地址，然后重新构建。

已验证
代码检查通过；构建仍等待配置补齐。
```

实际呈现时用粗体强调结论和小标题，执行摘要降低亮度。这个方向保留了“是否在工作、做了什么、是否失败、最终得到什么”，详细过程始终可追溯。

现有功能已经能提供部分缓解：打开命令折叠、保持思考预览、退出全局详情；`/thinking` 能临时隐藏思考，但用户文档注明它不持久化。它们还不能组成一致的默认体验，单纯换主题也不能压低过程信息量。

### 代码变更：清楚显示改动，默认控制长度

源码核实：`AssistantToolUseMessage` 在自动双栏门槛以下主要使用增删前景色，未给统一差异的代码行绘制对应背景；`SplitDiffView` 已有行背景、语法高亮和词级差异。主题也已有相应角色。因此优先统一已有能力，让常见窄屏获得同样明确的改动语义。

推荐呈现为文件名与增删统计、真实行号栏、红绿增删底色，以及行内改动强调。只有后端提供 patch 偏移时显示文件行号；普通 old/new 片段不能从 1 编造文件行号。预览、已应用、失败、拒绝与取消分别使用真实状态。

用户已明确移除“复制修改后代码”“展开原始差异”两个额外功能。代码与 Bash 的命令、代码、预览结果和展开正文都可单击展开、再点收起；不限定标题，也不加过渡动画。展开的仍是同一个块，保留普通选择复制，拖选与专用链接操作优先。

**长内容建议默认最多 8 个可视代码行**，这是本项目预算建议：短变更直接看完；长变更优先显示第一处完整改动和少量上下文，明确还有多少未显示；多个文件/修改片段共享预算；超长单行的续行也算在内。不能每个修改片段各给 8 行而使整张卡片失控。主动展开不自动收起，展开/折叠保持阅读锚点。

本次读取本机 Claude Code 2.1.302 发布包，确认它并非统一用一个截断数字：普通 Edit 结果有只呈现增删摘要和展开提示的分支；命令结果中的文件差异有 40 个源行的预览分支；差异中的超长单行另有 2000 字符保护及省略提示。它们是不同入口的实现观察，不是所有版本的保证。官方 [CHANGELOG](https://github.com/anthropics/claude-code/blob/main/CHANGELOG.md)也记录了超长差异单行截断和大差异渲染改进；[主题文档](https://code.claude.com/docs/en/terminal-config#diff-rendering)明确区分行背景与词级强调。

参照：[长变更折叠样稿](preview/edit-long-100-dark.png) / [超长单行样稿](preview/edit-long-line-60-dark.png)。这里验证展示，不把浏览器展开性能冒充终端表现。

## 5. 滚动：已有补丁为何仍不够

### 5.1 pi-plugin 的真实职责

`pi-plugins/extensions/dsh-scroll-speed` 给 **dsh-TUI** 安装包打补丁；Pi 在这里提供安装与状态命令，并不参与 dsh-TUI 每一帧的绘制。

本次确认：

- 正在检查的 profile 安装包是 dsh-TUI 0.15.0。
- 补丁状态为 `patched: yes`，helper 与备份存在。
- 实际安装的 helper 与 pi-plugins 中的版本逐字一致。
- 项目源码仍有两个固定 `±3` 的入口：指针命中滚动区域的入口，以及正文之外滚动的回退入口。
- 当前安装包的回退入口还保留上一版 `DSH_TUI_WHEEL_STEP` 规则，和新补丁的 SLOW/FAST 规则并存。

### 5.2 已通过真实安装包复现：鼠标位置改变滚动速度

我使用真实安装包的 Chat、输入解析与渲染器，注入虚构的 120 轮会话和固定滚轮序列。没有恢复用户会话，没有发模型请求。

| 相同输入 | 指针在正文区 | 指针在底栏区 |
| --- | --- | --- |
| 3 个事件，间隔 200ms | 移动 **1 行** | 移动 **3 行** |
| 24 个事件，间隔 8ms | 移动 **92 行** | 移动 **54 行** |

100×40 与 60×40 两种尺寸结果一致。数字是当前安装包加本地补丁的行为，不是未打补丁的上游默认值。

原因是：正文区域消费补丁算出的行数；底栏区域没有消费后，事件进入旧规则。当前补丁中，算出 0 行的事件会提前跳过，所以底栏的结果也不是简单的“事件数 × 3”。这是同一程序内真实存在的不一致。

### 5.3 已通过原 helper 回放：批次和反向会影响速度

helper 用 `performance.now()` 的处理时间识别小于 5ms 的事件批次，再统计 400ms 内的起始数。

| 确定性回放 | 产生的位移意图 | 含义 |
| --- | --- | --- |
| 24 个事件，间隔 8ms | **92 行** | 持续进入加速区 |
| 24 个事件同一时刻处理 | **8 行** | 被视为同一批次，没有相同加速 |
| 快滚后立即反向 3 个事件 | **反向 24 行** | 清掉小数余量，但保留此前加速历史 |
| 全新手势反向 3 个事件 | **反向 1 行** | 从慢速开始 |

这是同一份代码的确定性模拟，说明策略对事件处理节奏敏感；不等于用户真实操作一定以这些批次到达。输入阻塞、终端聚合和快速反向都是接下来应采样的场景。

另一个实际取舍：默认 `0.34` 行/事件会产生 `0、0、1` 的慢速输出。若终端每刻度只发一个事件，就可能前两格不动。只有在确实每格多事件的输入中，这种设置才可能接近每格一行。不能无条件承诺“慢滚一格一行”。

### 5.4 引擎已有基础；性能瓶颈仍需针对场景测量

源码已经实现：

- `ScrollBox` 累积滚动位移，输入通知按帧合并；目标帧间隔 16ms。
- 分帧消耗待滚动位移，慢滚与大位移有不同处理。
- 消息虚拟化、测量缓存和折叠后的阅读锚点修正。
- 终端区域滚动、增量补行和同步输出，在满足条件时使用。

**并非所有场景都会走区域滚动快路径。** 例如有较宽侧栏、图片、上滚同时内容增长等情况，会因正确性要求回退；不能因为代码里有快路径就认定真实使用已流畅。

本次内存输出探针中，100 列的 `onFrame` 渲染区间 p95 约 **2.24ms**，60 列约 **2.28ms**。这个值不包括真实终端显示，也不完整包含 React 提交前的工作；虚构记录还服从项目现有的历史折叠规则。它只能说明本次样本的绘制区间没有重现长卡顿，不能据此宣称端到端 60fps 或长会话性能合格。

需要另测的重点：超长单张 Bash 卡、展开思考、流式输出期间上滚、折叠/展开、侧栏开关、改窗口宽度、真实 Ghostty 的输入到显示延迟。

## 6. 项目层面的建议范围与优先级

| 优先级 | 建议交付的体验 | 依据与边界 |
| --- | --- | --- |
| 第一批：展示与选择 | 回答突出；过程有界；长差异可快速开关；Pi 风格选项卡；少装饰 | 减少占屏，保留必要信息、明确状态和后端能力 |
| 第一批：滚动一致性 | 正文、底栏和面板共享速度语义；反向与目标切换行为明确 | 已有可复现差异，适合聚焦修正 |
| 第二批：按需优化 | 在实际慢场景中缩短输入延迟、限制渲染工作量、保护阅读位置 | 需要性能记录决定改哪里 |
| 后续可选 | 每轮工具汇总、Focus 视图、实时调速预览 | 有新交互与状态规则，先确认再定规格 |

建议将已经验证有用的滚动能力纳入项目源码和设置，并定义旧补丁的退出条件，避免同一台机器上两套算法叠加。具体加速曲线应以用户输入设备上的回放为准，不能直接复制旧报告中的常量。

主要修改职责在 TUI 的呈现层、交互层与滚动输入层。一般不需要改变模型推理、工具执行或会话存储；展示折叠应始终保留原始记录。若新增最终回答识别，需要先补齐跨后端的语义依据。

不做这些改进的结果也很明确：换色仍会保留大段执行文本；只替换 emoji 仍会保留多处动画和不一致的状态标记；安装补丁仍会留下入口不一致、升级覆盖和状态漂移的问题。

## 7. 后续验收应该检查什么

这是建议的验收方向，尚未约定数值门槛或实施排期：

1. 同一条脚本无论有多少源代码行，默认卡片都服从可视行预算；完整内容可打开、复制和查找。
2. 思考持续生成时，紧凑视图高度稳定；失败与待审批事项始终可见。
3. 相同滚轮输入在正文与底栏产生相同位移语义；弹窗与侧栏不会误滚背后的内容。
4. 慢滚可精确定位，快滚覆盖长距离；反向、停止、切换滚动区域不会延续不合适的加速状态。
5. 用户上滚后，生成结束、思考折叠和命令完成都不抢走当前阅读位置；主动回到底部才恢复跟随。
6. 用同一组短/长会话与输入回放，在普通及窄窗口、inline/fullscreen 中验收。性能同时记录输入到首帧、帧间隔、提交/布局耗时、终端输出量，不能只看平均 FPS。
7. 默认聊天、思考、工具、子任务和底栏的自有文案不添加装饰性 emoji；同一状态使用同一套文字与符号，完成后保持静态。
8. 少装饰后，关闭颜色仍能辨别运行、完成、失败、等待回答与审批；必要状态信息仍可访问，用户内容、代码与日志的展示和复制不被删改。
9. 代码变更具备独立的文件、统计与增删层级；长改动、多个片段、超长单行共用可视行预算，代码/Bash 整块内容可连续开关，拖选不误折叠，不新增两个已删除的操作按钮。
10. 选项卡焦点不冒充已选，多选确认不暗加焦点项，Other 输入不被数字/空格劫持；多题可回看，缺项不能提交；授权仍以真实后端请求和原有结果约束为准。
